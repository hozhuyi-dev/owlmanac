In the [last post](../from-brute-force-to-cdcl/) I built a SAT solver and pointed it at puzzles someone else had made. This time it makes them. The Star Battle game in the next post needed 6,000 puzzles, a third each Easy, Medium and Hard, and I wasn't going to draw them by hand.

Star Battle is played on a grid split into regions. Each row, each column and each region holds the same number of stars, two on the 10×10 grids here, and no two stars may touch, not even at a corner. Making one sounds easy: draw some regions. The catch is that a puzzle is only any good if it has exactly one solution.

## Finding one versus ruling out the rest

Asking a SAT solver whether a puzzle has a solution is what it's built for. It either finds one, or it proves there's none. But "is this a good puzzle?" asks something else: is there a *second* solution?

The trick is to ask twice. Find a solution, then add a clause saying "not that one", and ask again. If the solver finds another, the puzzle is ambiguous. If it says there's nothing, then the first solution was the only one, and the solver's "no" is a proof, the same kind of proof as [the last post's](../from-brute-force-to-cdcl/#can-you-trust-it) "this has no solution". This one question, "is there exactly one?", is the oracle in the title. Everything below is a way of asking it cleverly.

You can try it on a small 6×6 puzzle with one star per row, column and region. Pick a colour and paint over some cells to reshape the regions. The solver answers after every stroke: no solution, exactly one, or two or more, with a second solution drawn in hollow stars where it differs from the first.

It doesn't take much to break a puzzle. Most small changes either leave no solution at all, or open up a second one.

## Three ways to ask the oracle

**Random regions.** The simplest method: grow ten random regions, ask the oracle, and keep the layout if it's unique. It works, but only about one random layout in 400 is unique, so it spends most of its time throwing layouts away.

**Choose the stars first.** Turn it around. Pick where the twenty stars go first, obeying the row, column and touching rules, then group them into nearby pairs and grow a region around each pair. Now the intended solution is valid by construction, so a layout can never fail by having *no* solution, only by having more than one. That alone makes it about six times faster. It's the same idea Sudoku makers use: start from a solved grid and work backwards.

</Figure>

**Two solvers arguing.** The third method is the one I was most excited about, because it's clause learning all over again. One SAT solver, the *proposer*, draws the regions. A second, the *checker*, looks for a second solution. Each one it finds becomes a new rule for the proposer: "your regions must break this solution". The proposer never makes the same mistake twice, just as CDCL never walks into the same dead end twice. When the checker finally finds nothing, it has proved the puzzle unique. This loop has a name, counterexample-guided synthesis (*CEGIS*), and it works for any puzzle, not just Star Battle.

It needs only about seven proposals per puzzle. But it was the slowest of the three, and the reason is instructive. Regions must each be in one piece, and that's surprisingly hard to say in clauses. My first try told the proposer about each broken region only after it drew one. It never caught up: there are so many ways to draw a region in pieces that in 2,000 rounds it never drew a single valid layout. Writing the rule out in full fixed that, but drawing connected regions inside a SAT solver stays expensive.

So the elegant method lost, and the simple one won. I kept all three in a small Rust crate, and the pool for the game comes from choosing the stars first.

For puzzles made of clues, like Sudoku, there's a fourth way that *is* elegant and fast: start with every clue showing, then remove them one at a time, putting a clue back whenever a second solution appears. A clue can only ever rule solutions out, so once a clue is needed it stays needed, and you end with a puzzle where every clue counts. That's how the 16×16 and 25×25 grids in the last post were made.

## How hard is it?

The game needs Easy, Medium and Hard levels, so every puzzle has to be graded. The obvious measure is how hard the solver had to work. But the last post showed that depends on the solver as much as the puzzle: switching on phase saving tripled the dead ends on one Sudoku.

So I grade by how far ahead a person would have to think. **Depth 0** means forced moves alone solve it: every step is "this is the only place left". **Depth 1** allows one "what if": "if I put a star here, the forced moves run into a contradiction, so it can't go here". **Depth 2** allows a "what if" inside a "what if". Of the 600 puzzles in the chart above, all but one need depth 1 or 2 (the odd one out, from random regions, needs more), so depth 2 is Hard.

Depth alone lumps together very different depth-1 puzzles, though. A "what if" is played out in your head, so what matters is how far you have to follow it. I count that in **rounds**: round 1 is every move the trial forces outright, round 2 is every move those force, and so on, until a rule breaks. "A star here leaves that region no room" breaks in round 1. Six rounds means holding six looks at an imagined board. A player takes the easiest step on offer, so the grader does too: at each point it takes the shortest chain it can find, and a puzzle's **length** is the longest of those it can't avoid. In the pool, depth-1 puzzles split about 60:40 at length 2, so Easy is depth 1 with chains of at most two rounds, and Medium is depth 1 with longer ones.

The grader only uses forced moves and trials, never the solver's search, and it plays out the forced moves itself, so its answer doesn't depend on any heuristic.

The solver feels the difference too, though mostly the depth. Across the 200 puzzles made by choosing the stars first, it learns a median of 28 clauses solving an Easy one, 37 solving a Medium one, and 74 solving a Hard one. A long chain of forced moves costs the solver almost nothing: what's hard is holding it in your head. Each learnt clause is a new rule about that particular grid, "these can't all be true at once". ## Where you and the solver disagree

Strong Star Battle players use counting. "These three regions sit entirely inside these three rows, so between them they hold all six of those rows' stars, and no other region can put a star there." It's a big step for a person, and a hard one for this kind of solver. It's the same reasoning as the pigeonhole problems, which are provably hard for clause learning. So a puzzle graded Hard here might feel quick to someone who spots the right count, and an Easy one might be slow going for someone who doesn't.
